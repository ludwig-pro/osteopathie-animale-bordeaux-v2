2026-07-15 audit. The deploy-level contact test and the operational Netlify
Forms acceptance are intentionally combined in plan 003 because they prove the
same boundary.

Execute plans in the order below unless the dependency notes explicitly allow
parallel work. Every executor must read its plan fully, honor its STOP
conditions, and run every verification gate.

## Plan-corpus execution prerequisite

Commit this complete `plans/` corpus together before executing any plan. Every
executor must create its branch or isolated worktree from a commit that already
contains this index and all 13 plan files; an executor must STOP rather than
stage or commit an untracked plan corpus on the implementation branch.

For parallel execution, one central coordinator owns this status table.
Executors report `DONE`, `BLOCKED`, or `REJECTED` plus evidence to that
coordinator and do not edit `plans/README.md` in their isolated worktrees. A
single sequential executor may update its own row directly.

## Dependency notes

- Plans 001, 002, 004, 007, 009, 010, and 013 are independent roots and may
  be started in parallel in isolated worktrees. Plan 013 has no code dependency
  but cannot pass its owner-validation gate until the named business owner is
  available and supplies a durable approval reference.
- Plan 003 follows 002 so its preview submission validates the final field
  contract. Plan 001 was rejected; the remote acceptance isolates analytics
  providers without claiming to test consent.
- Plan 005 follows 001 and 004 because it overlaps `BaseLayout.astro` and
  `MapSection.tsx`; demand-loading must preserve both consent-controlled
  preconnect state and the already-corrected destination fallback.
- Plan 006 follows 005 because both edit `BaseLayout.astro`; Plan 001 is already
  a transitive prerequisite through Plan 005.
- Plan 008 follows 007 because both restructure `.github/workflows/ci-quality.yml`.
- Plan 011 follows 010 because both edit the image wrappers and their React
  consumers.
- Plan 012 is the final consolidation gate. It deliberately follows all
  technical plans 001-011 so stricter formatting, lint, and type checks validate
  the final combined state instead of creating avoidable drift in every plan.
  For Plan 003, this means its first, repository-test-harness checkpoint; the
  later production/RFC/cancellation checkpoint may remain externally `BLOCKED`
  without holding back static-check coverage of the already-committed harness.
- Plan 013 is a decision spike. It must finish with an owner-approved decision,
  not speculative production copy or pricing changes. It remains independent of
  Plan 010 by citing stable path/symbol/claim fragments instead of line ranges;
  the coordinator reruns its inventory against the final integration candidate
  before marking it `DONE`.

## Findings considered and rejected

- Replacing Netlify Forms with a custom Cloudflare Worker: rejected by the
  existing RFC because it adds infrastructure to a low-volume form without a
  demonstrated reliability need.
- Removing `public/sw.js` or `public/service-worker.js`: rejected because they
  are intentional standalone cleanup workers for clients left behind by the
  Gatsby migration.
- Treating public GTM, Mapbox, PostHog, or reCAPTCHA identifiers as committed
  secrets: rejected; no private credential was found in the audited source.
- Adding a generic Content Security Policy as a top-priority security plan:
  deferred because the audit found no direct source-to-sink exploit path; the
  concrete consent, CI-token, and telemetry findings have higher leverage.
- Migrating React or Astro solely because newer major versions exist: rejected
  for this plan set because no current failure or removed API was demonstrated.
- A separate plan for the Netlify Forms RFC status: rejected as duplication;
  plan 003 owns both deploy evidence and RFC closure.
